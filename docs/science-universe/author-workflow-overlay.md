# 作者执行规则（优先于历史指令）

鼓励题目接近 Terminal-Bench-Science / Terminal-Bench 4.0；不要求证明明显区别，不以许可/合规或人工提案批准作为本轮阻塞。

## 提交审核前必须完成

1. 作者先检查题目格式、schema、输入输出、依赖、Docker构建、启动与verifier入口。
2. 使用实际题目容器至少完整解题一次，执行真实verifier，确认参考解通过、空/明显错误答案不通过。静态检查和宿主机跑通不能代替容器验收。
3. 根据真实运行结果反思、修改题目，并在修改后重新跑通。保存问题、修改、运行证据和残留限制，不允许仅写“自测通过”。
4. 基础格式、Docker/依赖、测试入口等问题全部解决后，才提交正式审核请求。未通过时只保留草稿/构建请求，不进入evaluator队列；平台构建服务可以协助作者，但平台缺陷不能转嫁给审核角色。
5. 控制面验收凭证必须绑定精确commit和执行快照，包含镜像digest、格式检查、真实容器启动、作者解题、verifier正负对照以及迭代后复跑证据。凭证过期、缺失或只含作者自述时不允许进入正式审核。

## 五小时迭代止损

每个出题思路累计主动迭代时间，跨会话累计，不因重启/换分支/改题名重置。主动实现、调试、分析和修改计时；纯ACS评测执行/等待时间不计，读取评测结果并修改的时间仍计入。只有可核验ACS运行区间可扣除，同一时间段不得重复扣除，也不得扣除同时在主动开发的时间。

累计主动迭代超过5小时仍未完成，立即停止该方向的进一步迭代，保存暂停/放弃说明、已有代码数据、证据、未解决项和可迁移经验，转向下一个思路。不得把封装、补文档或跨会话继续当作绕过预算的办法。

即使未满5小时，若已发现难度无法合理保证（例如多次合法简化后明显过易且没有可行改进路线），及时放弃换方向，不为制造难度收紧正确解集合、隐藏要求或增加无意义等待。不得把环境失败误判为高难度。

正式提交后请求独占评测并绑定版本；被接受后总结共享经验，考虑迁移到其它任务、领域、数据。

## 迭代记录命令

开始实现一个新思路时运行 role-iteration start <idea-id>；每次恢复会话先运行 role-iteration status <idea-id>。思路ID保持不变，账本跨会话保存在个人持久目录。等待真实ACS任务时运行 role-iteration acs-wait <idea-id> --acs-run-id <run-id>，返回主动开发前运行 role-iteration resume <idea-id>。等待期间不得同时开发该思路；审核前由平台按真实ACS记录核对扣除区间。计时工具使用保守墙钟累计，未明确记录的停顿不会自动扣除，停机维护区间应由平台核对后校正。

完成时运行 role-iteration finish <idea-id> --reason <证据路径与总结>；放弃时运行 role-iteration abandon <idea-id> --reason <未解决项与经验路径>。超过预算的方向不可通过重新start恢复。个人账本不是容器验收凭证，不能代替真实运行证据。

## 数值原型的最小检查

先用小规模、固定随机种子的例子验证原型，再投入长计算。检查空输入/空解集、数组形状、有限值、对数和平方根定义域、参数单位、极端参数及误差容限。参考解与生成真值必须使用一致的科学常数。命令退出码0不能代替产物、导入及verifier结果检查；多步骤自测使用set -e和pipefail，明确断言预期产物。
